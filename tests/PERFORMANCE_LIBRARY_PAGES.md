# تشخيص قوائم المواد والاختبارات والكليشة

هذه قياسات محلية باستخدام بديل Supabase داخل المتصفح، مع اعتراض **جميع** طلبات HTTP؛ لم تُجرَ قياسات أو استعلامات على Supabase الحقيقي. قورنت ملفات Commit التسليم `23949febaa5328d2b2245dab862b99334933ff98` بالملفات الحالية. زمن كل طلب في المحاكاة 250ms، مع جلسة صالحة، بيانات صغيرة، وثلاثة شعارات مختلفة ظاهرة.

| الصفحة | طلبات Supabase قبل | جولات متتابعة قبل ظهور البطاقات | طلبات بعد | جولات قبل ظهور البطاقات بعد | زمن مرحلة البيانات قبل ← بعد |
|---|---:|---:|---:|---:|---:|
| المواد | 9 | 2 | 1 | 1 | 514ms ← 254ms |
| قائمة الاختبارات | 3 | 2 | 1 | 1 | 536ms ← 277ms |
| الكليشة مع 3 شعارات | 6 | 3 | 1 للقائمة + 1 توقيع دفعة مؤجل | 1 | 780ms ← 275ms |

هذه الأرقام لا تشمل تنزيل ملفات HTML/JS أو الخطوط، ولا ملفات الصور نفسها، ولا طلب تحديث جلسة منتهية. الطلبات الإضافية للصور تعتمد على cache المتصفح. توقيع الشعارات يظل جولة إضافية مستقلة بعد عرض البطاقات، وليس جزءًا من مسار ظهور القائمة. بدون شعارات: الكليشة 3 طلبات ← طلب واحد. مع V مسارات شعارات مختلفة: القديم 3+V؛ الجديد طلب قائمة ثم دفعات الشعارات المرئية غير المخبأة فقط. إذا مرّر المستخدم الصفحة تظهر دفعات لاحقة عند الحاجة. لا توقيع إضافي لرابط صالح عند فتح معاينة نفس القالب أو الرجوع للصفحة.

## المسارات قبل الإصلاح

1. `requireAuth` يقرأ الجلسة المحلية، ثم `initNav` يطلب `get_my_role` بالتوازي مع تحميل القائمة.
2. المواد: أربع `fetchAll` متوازية: subjects، teaching_groups، subject_groups، questions(subject_id). لا طلب منفرد لكل مادة، لكن جميع أسئلة المستخدم تنقل لحساب الأعداد، وجميع خيارات نموذج التحرير تُجلب قبل الحاجة. غياب count يجعل كل قائمة غير فارغة ترسل range ثانية فارغة حتى مع ثلاثة أسئلة فقط. أربع طلبات بيانات + أربع نهايات فارغة + طلب الدور = 9.
3. الاختبارات: `fetchAll(exams)` تجلب ملخصات فقط بالفعل؛ لا N+1 ولا أسئلة أو كليشة كاملة. لكنها تسحب كل الاختبارات ثم طلب نهاية فارغ، إضافة إلى الدور = 3.
4. الكليشة: `fetchAll(letterheads)` تسحب جميع القوالب، ثم طلب نهاية فارغ. بعدها `Promise.all` يوقع رابطًا لكل مسار شعار مختلف. التوقيع كان متوازيًا، لكنه حاجز يمنع رسم كل البطاقات حتى يكتمل أبطأ شعار. الدور + طلبي قائمة + V طلبات توقيع = 3+V. مسح cache كله بعد حفظ/حذف قالب كان يعيد توقيع شعارات أخرى دون داعٍ.

## المسارات بعد الإصلاح

- RPC منفصلة لكل قائمة: get_subjects_page / get_exams_page / get_letterheads_page. أول طلب يرجع 25 عنصرًا بحد أقصى والعدد والدور؛ الصفحات التالية دون metadata. لا loop لجلب جميع عناصر القائمة، ولا طلب نهاية فارغ. ترتيب created_at ثم id يثبت الانتقال عند تساوي التواريخ.
- المواد تجمع الصفوف المرتبطة وأعداد الأسئلة في SQL واحد للمواد الظاهرة فقط؛ لا تنقل أسئلة البنك. خيارات نموذج الإضافة/التعديل تُجلب عند فتحه، بـcount دقيق يمنع طلب نهاية فارغ؛ لا تصبح نتيجة نموذج مغلق حالية عند فتح آخر.
- قائمة الاختبارات تستمر بملخصات فقط؛ فتح الاختبار نفسه هو الذي يجلب snapshots. جلب أسئلة ذلك الاختبار صار يطلب count لتجنب range النهاية الفارغة.
- الكليشة ترسم النصوص والأزرار فور وصول القائمة، ثم IntersectionObserver يحمّل شعارات البطاقات المرئية فقط. cache الذاكرة يحفظ وقت انتهاء، وpending deduplication، وcreateSignedUrls يوقع المسارات المطلوبة في دفعة. فشل شعار لا يخفي القوالب، ونتيجة بطاقة خرجت من الصفحة لا تكتب في بطاقة جديدة. تعديل قالب لا يمس cache المسارات الأخرى.
- الفهارس السابقة موجودة للمالك والمادة والعلاقات؛ أضيفت فقط فهارس `(user_id, created_at desc, id desc)` للترتيب المحدود في القوائم الثلاث. لم تُضف فهارس زائدة للعلاقات الموجودة.

RPCs القراءة SECURITY INVOKER، مع `auth.uid()` وsearch_path فارغ وحدود pagination، ولا تستقبل user_id. لم تتغير سياسات RLS أو Storage. تنفيذ الترقية الجديدة `20261030_library_pages_exam_revisions.sql` مطلوب قبل تجربة الواجهة على Supabase.

## إعادة القياس

```powershell
$env:NODE_PATH='مسار node_modules الذي يحتوي playwright'
$env:TQB_BROWSER_CHANNEL='chrome'
$env:TQB_RTT_MS='250'
# اختياري: نسخة محلية من HTML/JS/CSS السابقة للمقارنة
$env:TQB_BASELINE_DIR='مسار نسخة ما قبل التعديل'
node tests/library-performance.cjs
node tests/browser-library-exams.cjs
```

على الخدمة الحقيقية، المسار الأولي الآن يتطلب زمن RPC واحدة بدل جولتين أو ثلاث. لا يمكن استنتاج عدد ميلي ثانية مضمون دون قياس RTT وزمن تنفيذ SQL وCDN والجلسة في المتصفح الحقيقي. افحص DevTools بعد اعتماد الترقية: عدد الطلبات وشكل الاعتماديات قابلان للتحقق؛ زمن 1.5–2 ثانية لا يُنسب كله إلى SQL من الكود وحده.


## قياس فعلي بعد تنفيذ الترقية على Supabase الحقيقي

نُفذت الترقية بنجاح، ثم اختُبرت الواجهة المحلية مع جلسة المالك والبيانات الحقيقية، بثلاث زيارات لكل صفحة. هذه قياسات فعلية مستقلة عن المحاكاة أعلاه. الأرقام بالميلي ثانية:

| الصفحة | RPC (ثلاث عينات) | اكتمال DOM من بدء RPC | من بداية التنقل حتى اكتمال DOM |
|---|---|---|---|
| المواد | 433 / 279 / 298 | 435 / 280 / 299 | 669 / 378 / 401 |
| الاختبارات | 393 / 290 / 362 | 394 / 293 / 363 | 497 / 385 / 464 |
| الكليشة | 434 / 684 / 277 | 435 / 684 / 277 | 537 / 768 / 362 |

كل زيارة: طلب قائمة واحد. الكليشة ذات الشعار الفعلي أرسلت طلب توقيع دفعة واحد لاحقًا (331 / 579 / 283ms)، وظهر الشعار بعد 2315 / 2510 / 2104ms من التنقل، مستقلًا عن عرض القائمة. تشمل مدة الشعار انتظار الظهور وتنزيل الصورة وتأثير تبويب الخلفية؛ ليست مدة SQL. فتح معاينة نفس القالب لم يكرر طلب التوقيع.

لوحظت أيضًا عينة أولى شاذة لقائمة الاختبارات: RPC نحو 9830ms، ثم عادت القياسات اللاحقة إلى مئات الميلي ثانية. لا يوجد دليل كافٍ لعزو هذا الشذوذ إلى قاعدة البيانات أو الشبكة وحدها؛ تقليل الطلبات لا يضمن غياب تقلبات الخدمة.

`?measure=1` يضيف أرقامًا فقط إلى dataset للقائمة: rpcMs وlistReadyMs وpageReadyMs وpageRequests، وإحصاء توقيع الشعارات. لا بيانات مستخدم أو روابط موقعة أو tokens، ولا console أو شبكة تشخيصية إضافية. يقاس اكتمال DOM مباشرة لتجنب تضخيم requestAnimationFrame في تبويبات الخلفية؛ ليس قياسًا دقيقًا لأول paint.
